# @crewhaus/ui — web UIs for every harness shape

`@crewhaus/ui` is a drop-in, polished, shape-aware web UI for a **compiled
CrewHaus harness**. You compile a spec to a target, point `@crewhaus/ui` at the
compiled directory, and get a browser interface with a live activity feed: tool
calls, sub-agents, permission decisions, cost, model output, role hand-offs, and
eval verdicts — as they happen.

It ships on npm as the scoped library `@crewhaus/ui` (not the bare `crewhaus`
CLI). There's no build step and no config: the package detects your shape, runs
the bundle the way that shape demands, and renders the same `TraceEvent` stream
the structured printer emits.

## When to use it

Reach for `@crewhaus/ui` once you have a *compiled* harness and want to see it —
or drive it — in the browser instead of a terminal. It's the visual front end for
running a bundle. If you're still **authoring** a spec (browsing the workspace,
running the wizard, replaying old traces), that's [Studio](#relationship-to-studio)
— the two are complementary.

## Quick start (the one command)

Run from a directory that holds a compiled harness and its `crewhaus.yaml`:

```bash
bunx @crewhaus/ui        # detect the shape, write a 3-line runner, install the dep
bun crewhaus-ui.ts       # run it  ->  http://localhost:4100
```

`bunx @crewhaus/ui` auto-detects the shape from your spec's `target:` and the
compiled files, then writes a tiny local runner that "just works":

```ts
#!/usr/bin/env bun
// Generated by @crewhaus/ui — serves the "cli" UI for this harness.
// Run:  bun crewhaus-ui.ts
import { serve } from "@crewhaus/ui";
serve({ shape: "cli", harnessDir: import.meta.dir });
```

Open the URL and press **Start** (or **Run**).

### Worked example: a standalone harness directory

From the harness directory (its own `crewhaus.yaml` plus a compiled bundle):

```bash
crewhaus compile crewhaus.yaml -o build   # compile the spec to a shape
bunx @crewhaus/ui                         # detect the shape, scaffold a runner, install
bun crewhaus-ui.ts                        # run it  ->  http://localhost:4100
```

This works cleanly from **inside a standalone harness directory** — the CLI
resolves the spec and the compiled bundle from the current working directory
(it auto-checks `.`, `./build`, and `./dist`).

## The `crewhaus-ui` CLI

The package installs a `crewhaus-ui` binary. The default command scaffolds a
runner; `serve` runs the UI immediately without writing a file.

```bash
crewhaus-ui                  # detect the shape here, write a runner, install the dep
crewhaus-ui <shape>          # force a shape (positional)
crewhaus-ui serve [shape]    # run the UI now, no file written
crewhaus-ui list             # list available shapes
crewhaus-ui --help           # full usage
```

### Options

| Option | Default | Effect |
|---|---|---|
| `-d, --dir <dir>` | auto (`.`, `./build`, `./dist`) | The harness / compiled-files directory. |
| `-o, --out <file>` | `crewhaus-ui.ts` | The runner file to write. |
| `-p, --port <n>` | `4100` (or `$CREWHAUS_UI_PORT`) | UI port. |
| `-s, --serve` | off | Run the UI right after scaffolding. |
| `--shape <name>` | auto-detect | Force the shape, skipping detection. |
| `--force` | off | Overwrite an existing runner file. |
| `--no-install` | off | Skip the `bun add @crewhaus/ui` step. |

### Shape auto-detection

Detection reads the top-level `target:` from a spec, searching the harness dir,
its parent, and the cwd for `crewhaus.yaml` / `*.yaml`:

- A `.claude-plugin` directory → `claude-plugin`.
- A `worker.js` + `wrangler.toml` → `cf-worker-<target>` (default
  `cf-worker-cli`).
- Otherwise the spec's `target:` maps 1:1 to a shape.

If it still can't tell, it asks you to pass an explicit shape (e.g.
`crewhaus-ui cli`).

## Programmatic API

Everything the CLI does is exported, so you can wire the UI into your own
scripts:

```ts
import {
  serve,
  detectShape,
  scaffold,
  listShapes,
  readSpecTarget,
  resolveHarnessDir,
  PKG_ROOT,
} from "@crewhaus/ui";
import type { ServeOptions, ScaffoldOptions } from "@crewhaus/ui";

// The main call — boot the server for a compiled bundle.
serve({ shape: "graph", harnessDir: "./build", port: 4100 });
```

`serve({ shape, harnessDir, port? })` is the one you'll reach for most;
`scaffold`, `detectShape`, `listShapes`, `readSpecTarget`, and
`resolveHarnessDir` are the building blocks the `crewhaus-ui` CLI is made of.

## Shapes it supports

The package ships a UI for every first-class target shape, three `cf-worker`
variants, and the plugin inspector:

| Shape | What the UI gives you |
|---|---|
| `cli` | An interactive terminal agent as a chat, with a live activity feed (tools, sub-agents, permissions, cost). |
| `channel` | A bot operator dashboard — channels, live `/status`, an inbound-message simulator, activity + logs. |
| `graph` | A stateful DAG runtime — node graph that lights up as it executes, plus the result. |
| `workflow` | A step timeline for deterministic multi-step orchestration. |
| `crew` | A multi-role crew — roles panel + handoff timeline. |
| `pipeline` | A RAG pipeline — query in, retrieved sources/citations + cited answer. |
| `research` | An autonomous research agent — branch tree, sources, assembled report. |
| `batch` | A queue worker — job board + throughput. |
| `voice` | A realtime voice agent — transcript + voice-loop activity (type to simulate speech). |
| `browser` | A computer-use agent — action timeline + viewport info. |
| `managed` | A multi-tenant gateway — health dashboard + request console. |
| `eval` | An eval bundle — score board, per-case verdicts, report. |
| `onchain` | An event-driven EVM agent — contracts, wallet, tx activity. |
| `onchain-game` | A perceive-act game loop — game state + loop visualization. |
| `cf-worker-cli` | A Cloudflare Worker agent — streaming SSE request console. |
| `cf-worker-graph` | The graph runtime at the edge — SSE console + node progression. |
| `cf-worker-workflow` | The workflow runtime at the edge — SSE console + step timeline. |
| `claude-plugin` | A plugin inspector — manifest, MCP servers, README, install instructions. |

Run `crewhaus-ui list` to print the shapes your installed version ships.

## How it works

Each shape is a small static front-end backed by a single shared host
(`_shared/host.ts`). For a given harness the host:

1. **Detects the entry file** — `daemon.ts` › `agent.ts` › `worker.js`, in that
   precedence.
2. **Installs the bundle's dependencies on first run** by scanning its imports
   (the `@crewhaus/*` packages are all public on npm). Later runs are instant.
3. **Runs the harness the way its shape class demands:**
   - **stdio** shapes (`cli`, `graph`, `workflow`, `crew`, `pipeline`,
     `research`, `batch`, `voice`, `browser`, `eval`, `onchain`, `onchain-game`)
     are spawned as `bun <entry>`, with stdin/stdout bridged to the browser.
   - **daemon** shapes (`channel`, `managed`) are spawned on an internal port
     (assigned automatically via `PORT`) and reverse-proxied.
   - **cf-worker** shapes import the worker module and invoke its `fetch`
     handler directly; Server-Sent Events stream to the page — no `wrangler`
     needed.
   - **plugin** (`claude-plugin`) bundles are parsed and inspected; there's
     nothing to run.
4. **Streams `TraceEvent`s.** Bundles are run with `CREWHAUS_TRACE=json` (and
   `CREWHAUS_COST_TRACKING=1`). The host brace-matches the embedded `TraceEvent`
   JSON out of the interleaved stdout stream and renders tool calls, sub-agents,
   permission decisions, cost, model responses, role hand-offs, eval verdicts,
   and more.

That last point is the key one: `@crewhaus/ui` is a **consumer of the exact same
`TraceEvent` stream** that `CREWHAUS_TRACE=json` emits — the structured printer
and this UI render the same events. See
[Observability and cost](https://crewhaus.ai/docs/getting-started/observability/)
for the event grammar and the other ways to read that stream.

The front-end is dependency-free: a small DOM toolkit, a `TraceEvent` renderer,
shared chrome, and one CSS design system. All rendering is done with DOM nodes
and `textContent`, so a harness can never inject markup into the page — a
deliberate isolation property.

## Requirements

- [Bun](https://bun.sh) ≥ 1.2 (the same runtime CrewHaus bundles use).
- A provider credential so the agent can actually think, e.g.
  `ANTHROPIC_API_KEY` — see [Secrets & environment](#secrets--environment).

The first run installs the bundle's npm dependencies automatically; subsequent
runs are instant.

## Secrets & environment

Agents need credentials — a provider key, and maybe channel tokens or an RPC
URL. These live in `.env` files that are **never committed**; every folder that
needs one ships a `*.example` template. Copy it, drop in real values, and the
host loads it for you:

```bash
cp .env.example .env              # repo-root: applies to ALL shapes (a shared key)
cp <shape>/harness/.env.example <shape>/harness/.env   # …or per shape
```

The host loads `.env` files in **increasing precedence**: repo-root `.env` →
`<shape>/.env` → `<shape>/harness/.env`, and an exported shell variable
overrides them all. So a single `ANTHROPIC_API_KEY` in the root `.env` covers
every shape, and a `<shape>/harness/.env` can override it.

`cf-worker` shapes use Cloudflare's native format instead — copy
`<shape>/harness/.dev.vars.example` to `.dev.vars` (the same file `wrangler dev`
reads). Only the `.example` templates are tracked by git.

## Configuration

| Env var | Effect |
|---|---|
| `CREWHAUS_UI_PORT` | The UI port (default `4100`). |
| `CREWHAUS_SANDBOX=noop` | Disable the code-exec sandbox floor. |

Anything in a `.env` (or an exported variable) is forwarded to the harness;
`PORT` for daemon shapes is assigned automatically.

## Relationship to Studio

Studio (in the `crewhaus/utilities` repo) and `@crewhaus/ui` are complementary,
not competing:

- **Studio** is for spec **authoring** and **trace replay** — browse the
  workspace, run the wizard, lay out graphs, replay old runs. It does not need a
  compiled harness.
- **`@crewhaus/ui`** is for **running and visualizing a compiled harness**,
  shape-aware, live.

Use Studio to write and shape a spec; compile it; then use `@crewhaus/ui` to
run it in the browser.
