# access-control

Status: planned
Dependency phase: 7 - Permission/policy
Catalog layer: R8 - Permission, Policy, Safety
Origin in ordering: 0.9.0 ([#507](https://github.com/crewhaus/factory/issues/507), [#513](https://github.com/crewhaus/factory/issues/513))
Workspace home: packages/access-control
Targets: All (it governs who may operate a harness of any shape; it never enters a compiled harness, which reads only the approver projection this package writes)
Test layers: T1, T3, T8

## Purpose

Who is asking, and may they do this? access-control answers both for everything that operates a harness: Home (the Hangar console), the CLI, the decision service and, through the approver projection below, the daemons that take approvals from Slack. It owns principals, their credentials, the roles granted to them, and the links from outside identities (a Slack user, a GitHub account, a proxy login) to them. `authenticate()` turns a request into at most one principal; `authorize()` says whether that principal holds a permission on a target, or which permission it lacks.

Today the console has one secret. Whoever holds `<hangarRoot>/token` is "the operator": every `/api` route checks it the same way (`isAuthorized` in `packages/hangar-server/src/auth.ts`). That suits one person on loopback, not a teammate, a phone that only watches, a script or a reverse proxy. 0.9.0 adds members and service principals, roles granted per harness, per group or for the whole Home, and secrets the server keeps only as hashes and issues sealed to the client that asked. The existing token stays, as the owner's bootstrap.

The package is files in the Hangar root plus WebCrypto, with no model call and no network service. Daemons learn who may decide their approvals from an approver projection this package writes into each governed harness, so a revocation reaches them with Home stopped.

Not to be confused with `permission-engine` (brief 078), which decides whether an agent's tool call may run; access-control decides what a person or a service may do to a harness.

## Boundaries

Owns:

- **Principals** — a principal (`prn_`) is a `member` or a `service` ("member", because "person" belongs to the people-profiles domain). System actors (`sys:scheduler`, `sys:reconcile`, `sys:runtime`, `sys:executor`) never authenticate and appear only as the actors of background effects. The local actor `local:<user>@<host>`, the OS user who owns the Hangar root (a user name, because Windows has no numeric uid), is linked to the owner at first boot and acts for CLI direct mode, which needs no credential and always works locally. An append-only record never stores a raw `local:` id: it stores the linked `prn_`, or `local:#<keyed digest>` when the user is unlinked, and the readable mapping lives only in the rewritable `access/subjects.json`.
- **Credentials, hashed at rest** — secrets are random, and the access records keep only their sha256 (in credential `crd_`, session and invite records); a list shows a `prefixHint` and `lastUsedAt`, never the hash. The one credential left in the clear is the bootstrap's own file, which stays where the CLI reads it.

  | Credential | Held by | Lifetime | Accepted for |
  |---|---|---|---|
  | Bootstrap | the owner: the existing `<hangarRoot>/token` | until `crewhaus hangar rotate-token` | the owner, from a direct loopback peer only (below) |
  | Device key | the browser: a non-extractable ECDSA P-256 key; the server keeps the public key | until revoked; dropped after 30 days unused | signing a single-use challenge for a session |
  | Session `cha_` | the browser, in sessionStorage as today | 1 hour sliding, 12 hours at most | every `/api` route |
  | Personal token `chp_` | the CLI, in `Bun.secrets` or a 0600 file | 90 days | CLI remote mode and `crewhaus api`, capped at the member's grants |
  | Service token `chs_` | a script or integration, with an explicit permission set and harness list | 180 days, with a reminder before expiry | the `/api/v1` operations in its scope |
  | Scoped token `chx_` | an embedded viewer, minted by a service | 15 minutes at most | read actions on the runs it names, from the one origin it is bound to, a strict subset of its minter's; it cannot mint, decide or list |
  | Invite code `chi_` | the person invited | a day by default, a week at most; single use | accepting the invite |
  | Proxy identity | nobody: a header your reverse proxy sets | per request | only from a peer that proves it is the proxy |

  A scoped token is stored nowhere: it is an HMAC over its subject, runs, actions, origin, expiry and the minting service's epoch, so bumping that epoch revokes every token the service minted.
- **Sign-in** — the library behind each path; hangar-server mounts the routes and hangar-ui draws the screens. The boot ticket `crewhaus hangar` opens redirects to a single-use exchange code (`/#x=`), which the browser trades with its new device key for a session, so a browser holds a session, never the bootstrap; a tab from an earlier release is migrated once, from loopback. An invite link (`/invite#c=`) asks only for a display name, then creates the member, records the grant, enrols the device key and starts a session. The `--lan` QR code is a short-lived viewer invite unless `--lan-role` raises it. A returning browser signs a challenge with its device key. In a URL, a code travels only in the fragment, never in a path or a query string.
- **Device sign-in** — `crewhaus login --server <url>` runs a device-code flow over four operations: `auth.device.start` and `auth.device.poll` are public (behind the Host allowlist, rate-limited, pending requests capped), and `auth.device.lookup` and `auth.device.decide` need a signed-in member. Pending requests live in `access/device-requests.json`. The terminal prints a code and a link to Home's `#/device` page, and nothing is minted until a signed-in member chooses **Allow** there, or the owner runs `crewhaus access approve <code> [--deny]` on the Home host. The code is 8 letters, single use and valid for 10 minutes; the poll reference is a 256-bit secret that travels sealed. The personal token is issued sealed, capped at the member's grants (viewer with `--read-only`) and hashed in Home; no flag takes a token, and `crewhaus logout` revokes it. Plain `http://` to a non-loopback Home needs `--allow-http`, because TLS stays outside CrewHaus. One short-code helper here serves device codes and link codes.
- **Tab-only sessions** — a plain-HTTP `--lan` page has no `crypto.subtle`, so no device key and no sealed issuance. Accepting an invite there opens a tab-only session: the page mints a 256-bit secret with `crypto.getRandomValues` and sends it as `sessionSecret`, a field the contract marks secret, and Home keeps only its sha256 and returns no secret, so no route needs a masker exemption. The session lives in sessionStorage, ends with the tab, cannot refresh, carries the invite's role, works only on the `--lan` address and cannot manage access. The page says the connection is not encrypted.
- **Sealed issuance** — a request that returns a new secret carries `seal`, an ephemeral ECDH P-256 public key from the client. The server derives a key (ECDH, then HKDF-SHA256), encrypts the secret with AES-256-GCM and answers hex ciphertext with `Cache-Control: no-store`. A reverse proxy may log bodies and headers, and ciphertext in a log is useless; hex also passes every masker rule, so no route needs a masker exemption. Direct-mode `crewhaus access mint` prints to the owner's own terminal instead.
- **`authenticate(req, server)`** — at most one principal per request: a session, a personal, service or scoped token, a proxy identity, or the bootstrap under its rules. In trusted-proxy mode, a bearer and a proxy identity naming different principals are refused as `unauthenticated` (`identity_mismatch`).
  - **The bootstrap** is the owner only when the TCP peer is loopback and the request carries no `Forwarded`, `X-Forwarded-*`, `X-Real-IP` or configured identity header, so a reverse proxy on the same machine cannot relay it. In proxy mode, or after `crewhaus hangar rotate-token --socket-only`, only `<hangarRoot>/home.sock` accepts it, which also defeats TCP forwarders such as `ssh -L`. No setting accepts it from anywhere.
  - **Trusted-proxy mode** is owner configuration (`access.trustedProxy` in the Hangar settings: the identity header, the proxy's peers and public host names, and either a shared secret, stored as a digest, or a socket), refused at boot unless Home binds loopback. The identity header counts only from a listed peer that also sends the secret, or on `<hangarRoot>/proxy.sock`; anywhere else it is stripped, and a content-free line goes to `access/security.jsonl`. A listed peer that sends no identity is unauthenticated, never the owner, and an unlinked identity gets "ask the owner to invite you", never an account.
  - **The Host allowlist**, always on and checked before authentication on every path but `/healthz`: only `localhost`, the loopback literals, the address `--lan` or `--host` bound, the proxy's public names, the host of `links.baseUrl` (an owner setting: https, or http on loopback), the names in `access.allowedHosts` and `--allow-host` additions are answered; anything else gets 421. A DNS-rebinding page reaches loopback same-origin, but it carries its own `Host`, which a browser does not let it forge.
- **Grants and `authorize()`** — a grant gives a principal one of four roles (viewer, operator, maintainer, owner) at one scope: the whole Home, a registry group, or one harness. The highest covering grant is the role; there are no deny grants, and revoking removes. Services carry explicit permission sets instead of roles, and read metadata without content unless a grant adds it. `authorize(actor, permission, target)` is a pure function over an immutable snapshot of the access records, reloaded when the access revision moves, and answers `{allow: true, grant}` or `{allow: false, needs, role}`, so a refusal names what is missing. Some limits are code, not configuration: services and system actors never decide on their own authority. On their own authority they never resolve maintainer- or owner-class decisions, never create or widen a standing rule and never activate a deployment; a service resolves operator-class decisions only with an explicit grant, and only a service with an explicit grant may set a run's subject. A deadline fallback is no exception: it applies the outcome the harness's owner-approved agreement declares and is recorded as decided by that policy, never by the system actor that applies it. Creating a harness grants no role: a non-owner creator's owner-only choices become one owner-class decision that activation waits for, and with a single owner nothing waits.
- **Scoped tokens and origins** — service principals carry owner-set `browserOrigins` and `webhookOrigins`, and a `chx_` token carries its origin, so a request from any other origin is refused. Preflight is answered only for an operation that declares `cors: "scoped"` and a listed origin, never with `Access-Control-Allow-Credentials`. Scoped acts include `run.artifacts.read`, and `run.trace.read`, which only a minter holding `h.read.content` may delegate.
- **`registerDomain(name, checker)`** — hands every route of one kind to its own authorizer, whose permissions no workspace role implies. The people-profiles area registers `people` this way, and this package gives it the principal and `access.onChange`, which reports typed changes from access-snapshot diffs, so one process sees another's. Its caches listen to that, and acting on a revocation is `control-service`'s (brief 325).
- **Links and the subjects file** — a link (`lnk_`) ties a principal to `slack:<team>:<user>`, `github:<id>`, `proxy:<header>:<value>` or `local:<user>@<host>`. The append-only records in `<hangarRoot>/access/` hold no secret and no readable identifier, only ids, hashes, keyed digests and device public keys. Subjects, display names and contact details live in the rewritable `access/subjects.json` and in the approver projections (a local subject only in `access/subjects.json`), so erasing a person rewrites those files and appends a tombstone, and no append-only record ever held the subject. A Slack link comes from the owner (`crewhaus access link slack:<team>:<user> --member <name>`, which works with Home stopped) or from Slack's "Link your CrewHaus account" prompt, confirmed by a signed-in member. A link request Home mints also carries an 8-character code, for a phone that cannot open Home's address: a signed-in member enters it in Home, or `crewhaus access link --code <code>` confirms it in direct mode.
- **The approver projection** — `.crewhaus/run/control/approvers.json`, the harness-local file daemons and the runtime read because they must not depend on Home: the owner, `governedSince`, each member who may decide with the highest class they may decide, the linked outside identities, and `homeUrl` when `links.baseUrl` is set. It is written atomically, only for a harness with a non-owner grant or a linked identity, and only when a grant, link, revocation or role change touches it, from Home or from `crewhaus access` in direct mode; never at boot or by registration, so an install that never invites or links anyone never gets one. `crewhaus access sync` rewrites stale ones, and the resident service refreshes them. Because it can hold readable link subjects, Home's raw file browser never serves it. No file means single-owner mode: decisions from Home and the CLI count as today, and a Slack click is refused with "link your account", because nothing says who the clicker is. An unreadable file refuses. `governedSince` keeps approvals in flight at the upgrade from being stranded: a grant an older release recorded counts only if it was made before the harness was governed.
- **Bootstrap migration** — on the first 0.9.0 boot of a Hangar root with no `access/`: create the owner principal, link the local OS user to it, and record the existing token's hash as the bootstrap. The file stays where it is, so the CLI and other local tools keep reading it. `crewhaus hangar rotate-token` mints a new token and revokes the old hash; restarting never re-mints it. A phone paired with `--lan` pairs again. If nobody is ever invited, nothing else changes: a single-owner Home, where a browser holds a session. `ensureToken` and the boot tickets move here from hangar-server.
- **The `crewhaus access` library** — `invite`, `members`, `grant`, `revoke`, `link`, `unlink`, `tokens`, `mint`, `sync` and `proxy`, each over the same records Home reads and writes; `apps/cli` only parses and prints. Only the owner invites in 0.9.0. It also backs the `--no-auth` check: the flag keeps its loopback-only, single-user meaning and is refused once proxy mode is configured or a second principal exists.

Does not own: the id grammars and minters, the permission vocabulary and the role matrix, which are data in `control-contract` (brief 322) that this package evaluates; the record primitives (locks, claims, append-only segments, the keyed-digest helper) and the approver-projection reader (`control-records`, brief 324); the route table that gives each route its permission, the choke point's order, the masker, the CSP and the sign-in screens (`hangar-server`, brief 301; `hangar-ui`, brief 302); decisions, their classes, standing rules and receipts (`session-store`, and `control-service`, brief 325, which calls `authorize()`); the Slack signature check (the channel adapters); the people domain's authorizer and erasure (the profiles area); and classifying what an authenticated caller sends. Authentication is not classification: API input is classified at the `api` TrustOrigin.

## Inputs and Outputs

Inputs: a request, the Bun server it arrived on (for the TCP peer) and its listener (the TCP port, `home.sock` or `proxy.sock`); the `access.*` block of the Hangar settings; the records under `<hangarRoot>/access/`; a client seal key on every request that issues a secret; and the `crewhaus access` verbs in direct mode.

Outputs: a principal, or a refusal (`unauthenticated`; 403 for a proxy identity nobody linked, which is told to ask the owner for an invite; 421 for a foreign `Host`); `authorize` verdicts that name the missing permission; sealed secrets; appended access records and a moved access revision, which caches and open streams watch (the `access.changed` event carries ids only); rewritten approver projections in the harnesses a change touches; and content-free lines in `access/security.jsonl`.

## Dependency Notes

Depends on `@crewhaus/control-contract` (ids and minters, the permission vocabulary and role matrix, error codes), `@crewhaus/control-records` (appends and claims, keyed digests) and `@crewhaus/infra-utils` (file locks). The cryptography is WebCrypto (ECDSA verification, ECDH, HKDF, AES-GCM, HMAC) plus `node:crypto`'s constant-time comparison, so the package adds no third-party dependency.

Consumers: `hangar-server`, whose `access.ts` runs `authenticate()` and `authorize()` at the one choke point in `handle()` and calls `authorize()` again where a request escalates, such as a spec write that touches the security surface; `control-service`, whose decision service checks a decider's class; and `apps/cli` (`crewhaus access`, `crewhaus login`, `crewhaus logout`, `crewhaus hangar rotate-token`, the `--no-auth` check). The direction runs one way, from control-contract through control-records and this package to control-service, hangar-server and the CLI, so nothing here imports hangar-server or control-service.

It never enters a compiled bundle and moves no fixture bytes. A harness sees only the approver projection, a plain file control-records reads: immediately before a granted tool call runs, runtime-core checks that whoever granted it still holds at least the class the decision requires, which covers revocation and demotion in one check.

## First Implementation Slice

Lands across the core's PR train ([#507](https://github.com/crewhaus/factory/issues/507)), each stage wired to a caller in the same change:

1. **The package**, with the `crewhaus access` verbs in direct mode as its first caller: principals, grants, invites, links and the subjects file, hashed credential records, `authorize()` over the role, permission and scope matrix, `registerDomain()`, the projection writer and the bootstrap migration. The same change adds the `ch*_` shapes to the token shapes in both `redact.ts` copies (`packages/ir/src/redact.ts`, `packages/spec-patch/src/redact.ts`), so a leaked CrewHaus secret is masked wherever it appears.
2. **Owner sign-in**: `authenticate()` with the bootstrap rules and `home.sock`, the identity rule, `links.baseUrl`, the Host allowlist, proxy mode, the boot exchange, device keys and sessions, and sealed issuance, with `ensureToken` and the boot tickets moved in from hangar-server. Whether Tailscale Serve can send the proxy secret or reach the proxy socket is checked here, before any recipe documents it. Until hangar-server enforces its route table, every principal but the owner is refused with `authorization_unavailable`, and a test pins it, so `main` never serves a non-owner without authorization.
3. **Non-owner sign-in**, in the change that enforces the route table: accepting invites, the viewer `--lan` invite, tab-only sessions, service tokens, scoped tokens (accepted here and tested with tokens minted through this library, because the operation that mints them over `/api/v1` comes in stage 4), and the new `--no-auth` refusals.
4. **Later callers**: the decision service's class checks, Slack link requests, the `access.*` operations of `/api/v1`, scoped-token minting among them, and `crewhaus login`, which lands with `crewhaus api`: its personal token is what CLI remote mode and `crewhaus api` use against `/api/v1`. The browser's sign-in operations under `/api/v1/auth/` land with stages 2 and 3; the device-code flow behind `crewhaus login` lands with that command.
5. **The last stage**, each with what first needs it: `access.onChange` with revocation settling, origin-bound tokens with the SDK, and link codes with the Slack app.

## Study References

Today's token and boot tickets (`packages/hangar-server/src/auth.ts`) and the choke point they guard (`handle()` in `packages/hangar-server/src/server.ts`); the masker (`packages/hangar-server/src/mask.ts` over `isCredentialKey`), which is why records and requests name fields around it (`prefixHint`, `lastUsedAt`, `credentialRef`, and `deviceJwk` rather than `publicKey` for a device's public key) and why the Hangar settings block is `access.*` rather than `auth.*`, an exact credential key; the console's sessionStorage handling (`packages/hangar-ui/assets/js/api.js`); the `--lan` and `--no-auth` refusals in `apps/cli/src/hangar-cmd.ts`; registry groups (`packages/harness-registry/src/types.ts`) as the group scope; and today's security model in [HANGAR.md](https://github.com/crewhaus/docs/blob/main/HANGAR.md#security-model). Standards: the W3C Web Cryptography API, RFC 5869 (HKDF), RFC 8628 (the device authorization grant behind `crewhaus login`), RFC 7239 (`Forwarded`), RFC 9110 (421 Misdirected Request), and WCAG 2.2 success criterion 3.3.8 (an invite asks only for a display name). WebAuthn proper waits: it needs CBOR and COSE parsing, and the core adds no third-party dependency.

## Validation Plan

Catalog tests: T1, T3, T8. Primary risks:

- **A principal reaching more than its role allows**, which becomes a cross-harness leak once Home leaves loopback. `authorize()` is one pure function, tested over the whole role × permission × scope matrix, and hangar-server's deny matrix, a release gate, drives every route with really minted credentials of every kind: each role, a service token, a scoped token, a scoped token from another origin, an unlinked proxy identity, a bearer and a proxy identity that disagree, a forwarded bootstrap, a remote bootstrap and a rebinding `Host`.
- **A secret that leaks**: a scan of every file the package writes finds no secret it issued and the bootstrap token only in its own file, a fake proxy log of headers and bodies carries none, and the `ch*_` shapes are masked.
- **A forged identity**: a rebinding `Host` gets 421, a proxy header from an unlisted peer is stripped, and a bootstrap with `X-Forwarded-For` is refused. The bootstrap test also dials the machine's own LAN address, where the token must be refused, because a test that only dials loopback cannot tell a peer check from none.
- **A revocation that never reaches a daemon**: a revoke with Home stopped rewrites the projection, an unreadable projection refuses, and an expired or revoked session closes its open streams.

Residuals, named rather than closed. Separation between OS users who can write the Hangar root is policy, not a boundary. An agent's `Bash` or `RunCommand` runs as the same OS user, and no layer sees what a shell does, as [factory's `AGENTS.md`](https://github.com/crewhaus/factory/blob/main/AGENTS.md) documents. These records sit under [#507](https://github.com/crewhaus/factory/issues/507)'s runtime-state floor, with its documented limits. A script injected into an open Home page can use the device key while the page is open but cannot carry it away; no `innerHTML`, a CSP, short sessions, per-device revocation and no cookies (so no CSRF surface) narrow it.

Definition of done: `bun test packages/access-control/src` green; invites single-use and expiring; a device request minting nothing until a signed-in member allows it; erasing a person leaves no identifier in any append-only record; no credential stored in the clear except the bootstrap token's own file, as today; and no projection written at boot or by registration.
