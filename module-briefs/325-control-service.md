# control-service

Status: planned
Dependency phase: 18 - Deployment & studio
Catalog layer: F3 - Deployment & Operations
Origin in ordering: 0.9.0 ([#507](https://github.com/crewhaus/factory/issues/507), [#513](https://github.com/crewhaus/factory/issues/513))
Workspace home: packages/control-service
Targets: All (it operates harnesses of every shape from Home, the CLI and the resident service; it never enters a compiled harness, which enforces what it records through libraries the bundle already imports)
Test layers: T1, T3, T7, T8

## Purpose

The control plane's composition root. `wireControl(deps, { mode, areas })` builds the services that Home (the Hangar console), the CLI, the opt-in resident service and the Home-level Slack app all call, so pausing a harness, cancelling a run, approving a tool call or activating a deployment is one call writing one record, whichever of them a person uses. It is to operating a harness what `memory-service`, `model-service` and `evaluation-service` (briefs 296, 308, 315) are to memory, routing and the in-loop gates, except that it never enters a compiled bundle: daemons enforce what it records through libraries they already import, so a harness keeps running, deciding and stopping with Home closed.

| Mode | Host | What runs |
|---|---|---|
| `server` | Home in the foreground (`crewhaus hangar`) | the executor, boot recovery, the projector, the scheduler and the webhook receivers, while Home is open; after a reboot it reconciles state but never restarts a daemon it did not start |
| `resident` | the opt-in service `crewhaus hangar install` sets up (macOS and Linux) | the same with no window open, and it alone restarts daemons after a reboot |
| `direct` | the CLI, acting on a harness's own files | nothing in the background: it recovers that harness's unfinished commands, does the work and exits, with no Home and no credential |
| `client` | the CLI against a remote Home (`--server`, `crewhaus api`) | nothing locally: calls go to `/api/v1` with a personal token |

Today Hangar shows a deployment record that nothing writes (`packages/hangar-server/src/deployments.ts`), and only the job queue records work before running it (`packages/harness-supervisor/src/queue.ts`). Three rules hold across every surface:

- **Persist, then acknowledge.** A change's receipt is written before any surface answers. "Accepted" is never "done", and "unknown" is a state, not a guess.
- **A claim decides.** Whatever must happen once is settled by creating a claim file exclusively, never by a lock alone, because the shared file lock (`packages/infra-utils/src/file-lock.ts`) is stolen once it looks abandoned, as it can after a laptop sleeps.
- **Reads never write.** A GET, a list or a fold adopts, delivers, compacts and builds nothing.

## Boundaries

Owns:

- **`wireControl(deps, { mode, areas })`** — returns the services below for one of the four modes. A mode changes where calls land and what runs in the background, never what a call does, so a CLI verb and the matching Home control write the same record.
- **Composition by head** — an area's data is a module in `control-contract`; its running code is composed by head (a head being a program that runs the core: the CLI in direct mode, a foreground Home or the resident service). `control-service/src/areas.ts`, imported by every head, holds command executors, reconcilers, activation gates, retire revokers, spawn-environment providers and delegated action kinds, because the CLI runs recovery, activation and retire itself and imports from hangar-server only its start surface and the scaffolded-workflow file names. `hangar-server/src/v1/areas.ts`, Home only, holds v1 handlers, ref resolvers, capability providers, stream sources and views, receivers and callbacks, projections and sweeps. Area runtime packages import `control-contract` and `control-records`, never this package, and the services they call arrive in the handler or executor context, so there is no cycle. A test over the composed lists, and a boot check that stops with the reason, refuse duplicates, an operation without a handler (or the reverse), a ref kind without a resolver, a source outside the harness root, and a `people.*` permission with a role. The deny matrix, the GET purity sweep, the rebuild test and the field-name walk iterate the composition and assert their counts, so they cover the next area by construction. Projections build only in the projector; a write asks for a refresh with `nudge(name, harness)`, and its receipt says `done` only once the projector confirms.
- **Commands and receipts** — every change is a command (`cmd_`): claim the idempotency key, append `accepted`, then finish a quick kind inline (a decision, an operator-record write) or hand it to the executor and answer with the accepted receipt. A receipt holds ids, refs, digests and states, never arguments, inputs or secrets, and says of each effect whether it happened and whether a retry is safe. A request refused by authentication, authorization or validation writes nothing.
- **Idempotency** — an `Idempotency-Key`, scoped to the caller, the target and the operation, becomes a claim holding the command id and a fingerprint of the request, secret fields left out. The same key and request return the original receipt, even mid-run; a different request under the same key is refused. Keys are honoured for seven days and never stored raw.
- **The executor, reconcilers and recovery** — handlers are registered per command kind (the kinds are a closed list in control-contract). The executor re-authorizes the command's actor against the current access snapshot before `accepted → running`, system actors and the linked local owner excepted, acts through the owning library (for processes, the supervisor's verbs, never a spawn of its own) and appends the final state. Workspace commands are closed kinds that run no agent tools. A kind with an external effect registers a reconciler that answers done, not done or unknown, so nothing becomes `succeeded` unobserved; the core registers reconcilers for its own effects, and feature areas for theirs (a published PR, a Slack post). `commands.recover()` runs at every Home boot, after adoption and the job-queue restore, and before the CLI's first change to a harness: a command that never started, or is safe to repeat, runs again; any other is reconciled, and one still unknown raises "interrupted, needs a decision". A run is never re-executed automatically, except one submitted with `onInterrupt: "retry-once"`, which is retried once, as a new run under a claim, with its creator's current authority re-checked; every other interrupted run waits for a person, and a run parked on an approval stays parked. A `preparing` channel run whose process is provably dead becomes `interrupted {reason: not-processed}`. Home's job runner and the CLI's long-running verbs (`eval`, `optimize`, `compile`, …) share the harness's mutating lease, so the two heads never run conflicting work at once.
- **Runs and the deployment adapters** — `runs.create`, `get`, `result`, `cancel` and `resume`, with a new `crewhaus runs cancel` beside the CLI's `runs resume`. This package writes a run's rows until it starts (queued, preparing, paused, cancelled), and a queued row records `by`, its creator; from then on the process running it records it (runtime-core, or gateway-server's managed-runs library on a managed harness), and the reconcile sweep marks `interrupted` a run whose process died. An API run's input goes to a file under `.crewhaus/run/control/inputs/`, readable only by its OS user and kept 30 days after the run ends, and the run classifies it at origin `api` once, as the seed of its first top-level loop. Per shape family: `managedAdapter` (managed) queues the run in the harness and nudges the daemon to claim it, so an API run returns at once and survives a daemon restart; `jobAdapter` runs a supervised job under a root run — cli through a new `crewhaus run --input-file`, crew with the input as its brief on stdin, and the other one-shot shapes only where the compiled entry reads a seed on stdin — with argv from a closed vocabulary, so a request body never becomes a command line; and `daemonAdapter` (channel, batch, voice) answers `unsupported`, naming the shape's own intake. A control-API run is refused for a bundle compiled before 0.9.0, which lacks the capability: `runs.create` answers `unsupported`, naming `crewhaus compile`. While the executor is offline or the harness paused, a new run is refused, or, if the caller asks, held until it can start. Cancelling a queued run first takes the claim the managed follower takes to start it, so a cancel and a start never both win. A cancel stops a running run at its next model call or tool boundary and lists the external effects already done.
- **Deployments and activation** — the one writer of deployment records, from both heads (`crewhaus daemon start`, a new `crewhaus deploy activate`, Home's Start and Activate). A compile records a `prepared` artifact; an explicit activation by a person, never a service principal, or by a rule its owner turned on ([#513](https://github.com/crewhaus/factory/issues/513)), recorded as the rule's, makes it `active` under a generation claim, so two activations cannot both win; a rollback returns to an earlier artifact; and a legacy bundle started without a record is activated implicitly, without autostart. A record names its artifact by digest and spec hash, and a managed one also where its tenants' sessions live; a rehearsal run records the prepared deployment and the artifact digest it ran, so the creation area's activation gate can prove the artifact it activates was rehearsed. Activation also writes the harness's portable identity (`.crewhaus/run/control/harness.json`), which no scan or read does, so opening Home never dirties a git-clean harness. **Automatic starts verify the build:** a crash restart, reboot recovery or `autoCompile` runs only the active deployment's build. Until builds are kept, a `dist/` that is not the active build is refused, with the reason and an attention item. Once builds are kept by digest, an automatic start restores the active deployment's kept build, and refuses only when that copy is missing or fails its digest; `autoCompile` recompiles only the active revision, and only when that copy is missing. A person's activation records what `dist/` holds, and materializes the chosen build once builds are kept. **Activation gates:** one static list in the head-wide file runs inside the activate command under the generation claim, so every head runs the same gates; a failed gate answers `conflict` with `current`. The first is the protected-environment quorum, through `@crewhaus/deployment-controller/approval-gate`. One exception: an explicit `crewhaus daemon start` or `restart` by the local actor in CLI direct mode, after a manual compile, records an activation with `gates: not-run`, and never activates into a protected environment; from Home, `--server` or the SDK it refuses when `dist/` is not the active build.
- **Operator controls** — pause new work, resume, drain, stop, start, restart, disable and enable, each a command; `crewhaus daemon pause | resume | disable | enable` are the new CLI twins. Pause, resume, disable and enable write the operator record (`.crewhaus/run/control/operator.json`), then nudge the daemon over `crewhaus.control.v1` to re-read it; start and stop record there whether the harness is meant to run. This package is the record's only writer. A pause holds runs not yet started and lets running work finish. The daemon's confirmation is a second effect, so a receipt says "confirmed", "applies within a second", "applies when it starts" or, for a bundle built before 0.9.0, "recorded, not enforced". Lifting a restriction is an authorized record write, never a call to the daemon, which has no route that lifts one.
- **Retire** — dry run first, and refused while a daemon is live; a new `crewhaus retire --stop`, like Home's retire flow, stops and disables the daemon first. Each step is an effect on the receipt: stop and disable, then cancel queued runs, expire pending decisions, revoke standing rules, delegation rules among them, revoke connections through the retire-revoker slot (the dry run lists any other as a manual step), run harness-lifecycle's existing steps (state backup, compliance evidence, audit verify, the optional knowledge push, the spec registry's tombstones, then the archive), log the retirement in Home's lifecycle log so it outlives the archive, and archive the harness's registry row, never delete it. People data is left alone unless named.
- **Revocation settling** — the consume check stays as the backstop, and `settleRevocation` settles what a revoked principal left waiting, acting on `access.onChange` as the revoking principal, per harness in scope, on only what the revoked principal has lost the authority to do. It cancels their queued runs, rejects their accepted commands, supersedes unused grants whose decider fell below the decision's class (`decider-revoked`, so the decision is asked again), denies device sign-ins they allowed but the CLI has not collected, bumps a revoked service's token epoch, and lists their running runs (`--stop-running` stops them) and standing rules. Every effect goes on the revoking receipt, and `crewhaus access revoke <target> --dry-run` (`access.revocations.preview`) shows the list first. The resident service repeats an unfinished sweep; claims make a repeat a no-op.
- **The decision service** — `decisions.resolve`, the one path Home, the CLI's `approvals grant | deny | supersede`, the Home-level Slack app and the SDK all take to decide a tool approval (`appr_`) or a control decision (`dec_`); a channel harness's own Slack app reaches the same compare-and-set from inside its daemon. It runs session-store's compare-and-set (control-records' for a `dec_`) with the mode's authorizer, so the first decision wins everywhere and the loser is told who won. The actor is the authenticated principal, never a body field: from the CLI it is the local OS user, `--by` is only a display label, and a decision is refused when `CREWHAUS_AGENT_TOOL`, a new marker the `Bash` and `RunCommand` tools set on what they spawn, shows the caller is an agent's shell, an accident guard rather than a boundary. A note a decider adds is kept for people and never reaches the model. Above the approvals store it owns:
  - **authority by class**: the decider's role must meet the decision's `requiredClass` (operator, maintainer or owner). No service or system actor decides on its own authority: a service decides only operator-class decisions, and only with an explicit grant, and a system actor only carries out a fallback the agreement declares (below); a rule a system actor applies is its owner's decision, made in advance;
  - **supersede**: the explicit way to change a decided decision, a grant or a deny, before it is consumed, for a maintainer or above, with a reason code. It parks a fresh question that names the one it replaces;
  - **deadlines and fallbacks**: a decision has a fallback only when the owner-approved agreement in the harness's spec declares one, with no default, so an unanswered decision otherwise waits until it expires; past the deadline, the scheduler or the next writer applies the outcome the agreement declares (continue without the call, defer, pause the harness, or deny), recorded as `resolvedBy: "policy"` with the agreement's revision, through the same claim a person takes, so the two never both win, and a fallback never grants;
  - **standing rules**: owner-only, narrow (the approved call's exact operative values, `Tool(<value>)`), expiring (30 days by default, a year at most) and revocable. The metadata goes to `.crewhaus/run/control/standing-rules.jsonl`, and enforcement is a plain allow entry in `.crewhaus/settings.json`, whose strict schema never changes, so a pinned 0.8.x bundle still loads it; revoking or expiring a rule removes the entry, and a revoked or expired rule stops matching within a second, through a liveness check in `permission-engine`, cached for a second. A non-owner's "Always allow" grants the one call and files an owner-class proposal, and a tool-wide allow from an earlier release is shown to the owner to narrow or remove, never removed automatically. A second kind, `delegate`, writes no settings entry and the decision service reads it.
- **Refs and capabilities** — `refs.resolve` turns a qualified ref (`<scope>/<kind>/<id>`) or a bare canonical id into `{kind, href, url?, rev, revisions?, summary}`. `href` is `/#/i/<ref>`, a route Home owns, so links survive layout changes; `rev` is a deployment id, a run's or command's row count, or a decision's state plus a binding-digest prefix; and a harness carries `revisions {spec, deployedSpec, deployment, policy}`. A bare `hex16` id lists its candidates and asks for a harness, rather than guess. Capabilities say what each harness can honour, from `control-contract`'s `SHAPE_RUN_CONTROLS`, the bundle's build stamp, the daemon's status and its heartbeat. An unsupported entry names its reason and the verb that fixes it, so a pause a bundle cannot enforce shows as "recorded, not enforced", never as "Paused".
- **The projector and the streams** — one projector, started after boot so it never delays it, folds each harness's control records into `<hangarRoot>/cache/index/`: a per-harness overview (the active deployment beside the saved spec, the operator state, runs by state, open decisions, the heartbeat's age), an index for bare ids and the fleet change log. Reads answer from it with `asOf` and `stale` or fall back to a bounded direct fold, and never build it; deleting it rebuilds the same answers. The run and harness streams read the records through control-records' cursors and the fleet stream tails the change log, so a resume reports a gap or a reset instead of guessing, and a list carries the position it was computed at, so "list, then subscribe" has no gap and no duplicate.
- **The scheduler** — one timer wheel on an injected clock, run by the resident service and by a foreground Home while it is open, for the writes no read may do: decision deadlines and fallbacks, standing-rule and claim expiry, segment retention, notification delivery (the rules and senders are `@crewhaus/attention`'s `./notifications`, planned brief 331) and the reconcile sweep. After a reboot only the installed resident service restarts daemons, through the supervisor, and it restarts only an active, enabled deployment that is meant to run and marked to autostart, both changed only by an explicit start, stop or activation, so a daemon stopped by hand stays stopped. A foreground Home reconciles state but never restarts a daemon it did not start, so without the service nothing restarts after a reboot, and Home says so. Each action is logged to `<hangarRoot>/service/recovery.json`.
- **The ingress registry** — `ingress.register(provider, { verify, dedupeRef, origin, handle })` refuses a webhook receiver that declares no TrustOrigin for the text it carries: `channel` for the chat text the Home-level Slack app passes on as conversation, while a command submitted through the app, such as starting a run, is control-API input at `api`. A receiver verifies the signature, claims the delivery id (Slack's `event_id`, GitHub's `X-GitHub-Delivery`), writes the inbound receipt and acknowledges within Slack's three seconds, leaving the work to the executor.

Does not own: the contract — ids, refs, state machines, error codes, events, the operation table, permissions and `verifyDecision` (`control-contract`, brief 322); identity and authorization, the approver projection included (`access-control`, brief 323); record formats, locks, claims, cursors and the lease file (`control-records`, brief 324), so this package never opens a control file directly; the tool-approval compare-and-set and the consume claim (`session-store`; runtime-core parks, consumes and re-checks a grant itself); how a daemon honours a control — lanes, loop admission, the gateway's `paused` and `disabled` answers, queue pulls and the control.v1 routes — and managed run semantics (gateway-protocol, runtime-core, gateway-server, queue-consumer); the per-daemon Slack approval path (a channel harness's own Slack app), which runs inside the channel daemon and so works with Home stopped; process supervision (`harness-supervisor`, brief 305), registry identity (`harness-registry`, brief 303) and retire's existing steps (`harness-lifecycle`); HTTP — the route table, the choke point, the receipts middleware, the v1 router, masking and the listeners (`hangar-server`, brief 301); notification rules, the attention inbox and the feature areas' own reconcilers, which `src/areas.ts` only composes; and the spec registry's environment pins behind `crewhaus deploy promote | rollback | canary` (`deployment-controller` and `canary-controller`, briefs 235 and 237).

## The delegation service

Status: planned

An owner can let the control plane decide one narrow kind of `ship` decision ([#517](https://github.com/crewhaus/factory/issues/517)). It is off until the owner turns a rule on, and it adds no package. A rule never gives a harness's agent a tool, a permission rule or a settings entry.

- **`applyDelegations`.** A scheduler sweep, every minute in the resident service or a foreground Home and once per `crewhaus delegations apply`, never on a read. For each open decision a rule claims, it evaluates the rule's gates, logs every verdict, asks `authorizeDelegated`, writes the rollback plan, then resolves the decision through the claim a person uses, so the first decision wins. The record says `resolvedBy: "delegation"`, applied by `sys:scheduler`, and names no person as the decider.
- **Effects.** Each is a receipted command by `sys:executor`, with the rule as its authority, and `verifyDecision`'s delegated branch re-checks the rule, the owner's authority and every bound revision, uncached. Any failure leaves the grant unspent and asks a person again.
- **The action-kind slot.** `control-service/src/areas.ts` holds each action's gates, signals, rollback planner, executors and preview terms. It has three members: `merge` (brief 333), `adopt` (brief 330) and `rollout`, below.
- **The watch and the rollback clause.** A watch starts from the effect's receipt, and a signal with no data is `unknown`, never healthy. A regression rolls back at once under the rule's rollback clause, which outlives a pause or revocation, then suspends the rule and raises one urgent item. A rollback is tried once; if it cannot finish, a person gets the exact remedy.
- **Turning one on.** An owner-class decision, in Home or with `crewhaus delegations enable … --confirm <harness>`, never from Slack or the SDK. The server renders a consequences page from closed templates, the owner types the harness name, and the decision binds the page's digest. The ceiling in `permissions.delegation` is read only from the active deployment, a rule lasts 14 days by default, and it can be revoked within a second. `permissions.delegation` is owner-only and never optimizable ([#514](https://github.com/crewhaus/factory/issues/514)); a rule's terms only narrow it, and no service or system actor creates, widens or resumes a rule.
- **`delegations.*`** operations and the `crewhaus delegations` verbs, and a retire revoker, since retiring a harness revokes its rules.

**The `rollout` action.** With a `rollout` ceiling, each prepared build that differs from the active one raises one rollout decision, bound to its artifact digest. A person decides it, or a rule when its five gates pass ([#516](https://github.com/crewhaus/factory/issues/516)): rehearsal, policy, activation, held out and one at a time. The effect goes through [#507](https://github.com/crewhaus/factory/issues/507)'s activation claim, the claim a person activating at the same moment would take, and the record carries `activatedBy`. A regression during the watch rolls back to the previous kept build, which must verify by digest before the rollout acts. This action arrives with `feat(quality-service): routine improvements and saved revisions roll out under an owner's rule, watched, with an automatic rollback`.

The service lands with `feat(control-service): an owner can delegate a narrow action under a rule that expires, can be revoked and is checked before every use`.

## Inputs and Outputs

Inputs: `deps` — the Hangar root, the harness registry, the supervisor, the control.v1 client and the mode's authorizer (Home's live access records, or the local authorizer in direct mode), with an injected clock and process operations so tests can drive time, crashes and reboots; in `client` mode, a server URL and a personal token instead. Each call carries an actor (a principal, the local OS user, or a system actor such as `sys:scheduler`), a target ref, the input and an optional idempotency key.

Outputs: receipts, in the harness's command ledger (`.crewhaus/run/control/commands/`) or Home's (`<hangarRoot>/control/commands/`), which Home and `crewhaus commands list | show` read back; run rows, deployment records, the operator record, standing rules and control decisions; refs, capabilities, lists and event streams; and the disposable projections. Every surface words its answer from the receipt: `/api/v1` answers 200 only for a finished, succeeded receipt, 202 with the receipt otherwise, and `unavailable` when nothing was done; the CLI exits 0 only on success, and otherwise through `EXIT_FOR_ERROR`'s band 50-56; and Slack says "Received" once the receipt exists, then updates the message from its final state. A Slack approval is answered once the decision is recorded, and the card updates off the request path.

## Dependency Notes

Depends on `@crewhaus/control-contract`, `@crewhaus/control-records` and `@crewhaus/access-control` (briefs 322 to 324), `@crewhaus/session-store` (`decide`, `supersede` and the read-only fold), `@crewhaus/harness-supervisor` (its verbs, the job queue, run detail and the job kinds), `@crewhaus/harness-registry`, `@crewhaus/harness-lifecycle`, `@crewhaus/gateway-protocol`'s `./control-client`, `@crewhaus/deployment-controller`'s `./approval-gate` (the first activation gate) and `@crewhaus/permission-engine` (writing and removing settings rules, and the narrow-pattern helper). Consumers: `hangar-server` (HTTP, in the foreground and as the resident service), `apps/cli` (direct and client modes) and the Home-level Slack app's connector.

It tops the control stack and is the only one of the four control packages that starts and stops processes (through the supervisor), so it never enters a compiled bundle: daemons enforce pause, disable and decisions through libraries bundles already import (runtime-core, session-store, gateway-protocol, gateway-server and queue-consumer, which reach the records through control-records), and the managed run library lives in gateway-server's light `./managed-runs` subpath rather than here. It never imports `hangar-server`: the shared helpers moved to lower packages, and `hangar-server` re-exports them for one release. That zero-behaviour extraction moved the control.v1 client to `packages/gateway-protocol/src/control-client.ts`, and run detail, the env and scrubber helpers and the closed job vocabulary to `harness-supervisor`. Session-root resolution and the read-only approvals fold land in session-store with first-decision-wins, where tool-approvals adopts both and gateway-protocol's control module adopts the fold for its pending-approvals count. A guard test (`apps/cli/src/hangar-server-imports.test.ts`) fails if `apps/cli` imports `@crewhaus/hangar-server` for anything but its start surface and the scaffolded-workflow file names.

It adds no spec key, no IR field and no codegen: unlike `wireEvaluation`, `wireControl` is never rendered into a bundle, and everything it writes is operational metadata. It makes no model call. Every package that imports it declares it in its own `dependencies`, checked on the installed tarballs as well as the checkout, because an undeclared workspace import works in the tree and breaks only once published.

## First Implementation Slice

Lands across the core's PR train ([#507](https://github.com/crewhaus/factory/issues/507)), scaffolded like its siblings from `packages/routing-store/package.json`, in two parts that each wire what they add:

Later PRs in the train extend the package in place: deployments and activation, with the gate slot; the operator controls and retire as commands, with the retire-revoker slot; the `/api/v1` operations and `runs.create` through the adapters; the scheduler, reconcile sweep, reboot recovery and receivers; and the streams and projector. The core's last PR, its release gate, runs a cross-surface acceptance suite against these libraries with faults injected, and revocation settling follows it. This brief lands in crewhaus/docs before the package does, because the factory admits no new package without a module brief.

## Validation Plan

Catalog tests: T1, T3, T7, T8. Primary risks:

- **A false "done"**: receipts are written before any answer, nothing becomes `succeeded` without an observation, and an uncertain outcome stays `unknown` until a reconciler settles it.
- **An effect that happens twice** (a retried request, two surfaces deciding one approval, two activations, the CLI and Home running one command): every exactly-once fact is a claim, executors act only through supervisor verbs, and a repeated settling sweep is a no-op.
- **Authority taken from the request** (a body field, a CLI flag, an agent's own shell): the actor is the authenticated principal or the local OS user, classes set who may decide what, and no service or system actor, on its own authority, decides above operator class, creates a standing rule or activates a deployment; a rule a system actor applies is its owner's decision, made in advance.
- **A read that writes**: a test drives every read against a fixture fleet and asserts that every file is byte-identical afterwards.
- **Home becoming load-bearing**: direct mode decides, stops, pauses, disables and retires with Home stopped, writing the same records Home reads, and a CLI recovery runs an area's reconciler.

Residual, named rather than closed: an agent's `Bash` or `RunCommand` runs as the same OS user and can run `crewhaus` itself. These records sit under [#507](https://github.com/crewhaus/factory/issues/507)'s runtime-state floor, with its documented limits. `CREWHAUS_AGENT_TOOL` makes the CLI refuse a decision from a tool's child process, but no layer sees what a shell does, as [factory's `AGENTS.md`](https://github.com/crewhaus/factory/blob/main/AGENTS.md) documents.

Definition of done: `bun test packages/control-service/src` green, with these pinned: a crash between persist and execute is dispatched again; a repeated key gives one effect and a different request under it a refusal; every mutating route writes exactly one receipt and a refused request none; the CLI and Home share one command ledger; Hangar, the CLI and a simulated Slack bridge racing on one approval give one winner; a non-owner's "Always allow" gives a one-off grant and a proposal; a repeated settling sweep changes nothing; a CLI recovery runs an area's reconciler; every `settings.json` a 0.9.0 head writes parses under the 0.8.x schema; an automatic start refuses a `dist/` that is not the active build; a failed gate answers `conflict` and activates nothing; `gates: not-run` never activates into a protected environment; a command whose actor lost the permission is refused before it runs; and a `retry-once` run re-checks its creator's authority. The train's cross-surface acceptance suite passes against these libraries.
