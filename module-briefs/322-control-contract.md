# control-contract

Status: planned
Dependency phase: 1 - Foundations
Catalog layer: R17 - Infrastructure & Cross-Cutting
Origin in ordering: 0.9.0 ([#507](https://github.com/crewhaus/factory/issues/507), [#513](https://github.com/crewhaus/factory/issues/513))
Workspace home: packages/control-contract
Targets: All (a contract whose main entry has no dependencies, not wired per shape: runs take their ids from its minter, and Home, the CLI and the SDK speak its operations)
Test layers: T1, T2, T9

## Purpose

The one description of the control plane that every surface shares: what each id looks like, which states a run, a command, a decision and a deployment can be in and how they move, what each permission is called, what every operation of the `crewhaus.hangar.v1` API takes and returns, and what an error, an event and a capability look like on the wire. It holds types, data, minters and a few pure functions; it opens no file and makes no network call.

In 0.9.0, Home (the Hangar console), the CLI, the background resident service, the daemons, Slack and the SDK all act on the same control records. A grant made in Slack, shown in Home and listed by the CLI is one decision with one id and one state only if all three read it through the same shapes. Today those shapes have no single owner: the session-id grammar is copied by hand across many packages, run ids come in several shapes from separate minters, and the console's route map is a file the UI and the server keep in step. This package gives them one, the way claim-ledger did for the citation grammar (brief 314).

Its main entry point, `.`, has zero dependencies: it imports no package and no `node:` module, so the planned SDK, `@crewhaus/client`, can bundle it for Node, browsers and Workers and ship with no runtime dependency. A second dependency-free entry point, `./http`, is the fetch transport and SSE reader that `crewhaus api` uses and the SDK wraps. Both are Node-clean source: relative `.js` specifiers, no `Bun.*` and no `node:`, held by a NodeNext type-check. The published package itself targets Bun, like every workspace package. The zod validators live in a separate entry point, `./schemas`, which the server uses to check what it receives.

## Boundaries

Owns:

- **Area modules.** An area module is static data, one file per area under `src/areas/`, of the type `AreaModule`: `{area, operations, refKinds, eventFamilies, machines, commandKinds, permissions, scopedActs?, reasonCodes?, capabilityKeys?, grammars?, rawExclusions?}`. So it declares the area's operations, ref kinds, event families (each type with a sensitivity), state machines, receipt kinds and permissions, and optionally its scoped acts, reason codes, capability keys, id grammars and file-browser exclusions. `AREA_MODULES` composes them, the core's module first, and each closed vocabulary below is the union of the modules, closed per build. An area's state machines are entries in `MACHINES`, checked by `canTransition()`, never separate transition exports. An area permission names its lowest role and whether a service principal may hold it; `people.*` has no role, and only the people domain decides it. Modules have no dependencies, so `@crewhaus/client` bundles them all.
- **Ids and refs.** The grammar of every id that crosses a surface, and its minter. Existing grammars do not change: `hrn_` harnesses, `sess_` sessions, `appr_` tool approvals, `grun_<16 hex>` graph runs, and `run_<16 hex>`, which is four families: executions (one process lifetime of the supervisor), eval runs, research runs and job logs. Every new object gets `<prefix>_<ulid>`, a lowercase ULID: a millisecond timestamp, then random bits from `crypto.getRandomValues`, so ids sort by mint time and never share a length with an older `run_` id. `dec_<ulid>` names a decision that is not a tool approval. `mintRunId()` mints the canonical run id, which run-context and runtime-core will use by default. `classifyRunId` tells the forms apart: a `run_<16 hex>` id answers `hex16` rather than name one family on grammar alone. The prefixes feature areas will mint are reserved here too, and a module may register a non-ULID grammar: attention's content-derived `att_` is `digest`, so `parseId` never decodes a time from it. A **qualified ref** is `<scope>/<kind>/<id>`, the scope a harness id or `home` and the kind from a closed list; the contract parses and prints refs, and control-service resolves them. Everywhere else ids are opaque, and grammars, minters and refs are imported, never re-declared: a pin test holds each known copy equal to the contract's until its package is next touched and the copy becomes an import. There are too many copies today for a check that fails on a second definition. The contract also holds the shapes a run row is built from: `Trigger {kind, lane?, via?, workItem?, synthetic?}`; `laneId`, one of `heartbeat`, `schedule` or `schedule:<name>`; `resumeScope`, one of `session:`, `job:`, `lane:`, `run:` or `work:`; and the optional row fields `sessionAt` (the session log's byte length at loop start), `cause {kind, ref}` (names and ids only) and `by` (who created a queued run).
- **The state machines, as data.** One `MACHINES` table, which gives runs, commands, decisions and deployments each their `states`, `entry`, `terminal`, `transitions` and `recoveryOwner`, and `canTransition()`, through which every reader and writer checks a move. A run is queued, preparing, running, waiting for an approval or an input, or paused before it starts, and it ends succeeded, failed, cancelled or interrupted. A command is accepted, then runs, and ends succeeded or failed; it can instead end rejected, when a precondition fails as it executes, or cancelled before it starts. One whose outcome nothing observed is `unknown` until reconciliation settles it. A decision is pending until it is decided, a grant or a deny, and a grant is spent once, when it is consumed. A decided decision, a grant or a deny, can be superseded before it is consumed, by a maintainer or above with a reason code, and a pending one can be superseded too. A pending decision can expire, and so can an unconsumed grant. A deployment is prepared, then active, then superseded or disabled, then retired, and a disabled one can be enabled again. `recoveryOwner` names who is responsible for recovering an object in each state: the control core for queued or preparing work, the runtime for a running run, the decision itself for one parked on an approval, the attention inbox for one waiting for an input, and the operator for paused or interrupted work. Two promises live in the data: a run parked on an approval stays parked when its process ends, and `interrupted` is terminal, so a retry is a new run with new authorization. A reader that meets an illegal row keeps it and shows it as an anomaly, but never applies it.
- **Pure checks.** `effectiveRunState`, `effectiveDecisionState(record, overlays, now)` and `verifyDecision` compute from records the caller has already read and a time it passes in, so a read can show that a decision has expired, or that its fallback is overdue, without writing anything; only a writer records the change. A decision view may carry `deferredUntil?`, `escalation?` and `sensitivity?`; `effectiveDecisionState` reads a tool approval's deferral from the record, and overlays keep `assigned`. `verifyDecision` is what runtime-core runs just before it spends a grant: the record is still an unconsumed, unexpired, unsuperseded grant; the consuming run is in the scope the grant was given in (the same session, queue job, scheduled lane or root run, or the work item, once work items exist) and is, or continues, the run that asked; the deployment and spec revisions, and the tool's resource revision where it declares one, still match; the places the call acts on are still the ones approved; and whoever decided may still decide it, according to the harness's approver projection (brief 323), while a harness with no projection has a single owner, as today. Current policy and the pre-tool hook stay runtime-core's own check. A failure names its reason, and the answer is always to ask again. The reason vocabulary includes `decider-revoked`, `people-erased`, `people-grant-revoked` and `erased`. Because the check is pure and lives here, runtime-core never imports control-service; because it reads no run records, turning run tracking off cannot weaken it.
- **The permission vocabulary and the role matrix, as data.** A closed set of permissions (`home.read`, `h.read`, `h.read.content`, `h.control`, `h.run.submit`, `h.decision.resolve`, `h.deploy`, `h.spec.edit.security`, …) and four roles, viewer, operator, maintainer and owner, each holding everything the one below it holds. Reading a harness's metadata and reading its content are separate permissions. Two kinds never come from a role: `h.subject.assert`, which only an explicit grant gives a service principal, and the people-profile permissions. A decision's class names the lowest role that may resolve it. Deciding whether a principal holds a permission is access-control's `authorize()`; the contract only holds the vocabulary and the matrix as data.
- **The operation table.** `OPERATIONS` has one row per operation, `{id, method, path, permission, receipt, request, response, cliTwin}`, composed from the core's module and one module per area, so that feature areas add operations without touching each other's files. A row may also carry `modelBound`, `summary`, `consequence`, `rung` and `cors`. `modelBound` gives each free-text request field either `{origin, at: "write" | "run-entry"}` or `none` with a reason, so text bound for a model is declared field by field; `summary`, `consequence` and `rung` are copy for the surfaces that show the operation, and `cors` marks an operation a scoped token may call across origins. `GET /api/v1` publishes it to signed-in callers, Home builds its paths from that discovery document instead of a second route map, `crewhaus api <operation>` drives it, and the protocol reference and an OpenAPI document are generated from it. A CLI twin is a real command from a closed argv vocabulary, or `null` with the reason, never a manufactured one. Twins are `{argv}` templates, a flag being a `--flag {param}` pair; `renderTwin` and `parseTwin` turn a template into a command line and back, round-trip tested, so the CLI can map its argv back to an operation. The wire id defaults to `crewhaus.hangar.v1` under `/api/v1`, named apart from the daemons' `crewhaus.control.v1` and the managed `crewhaus.v1`; the name is [#507](https://github.com/crewhaus/factory/issues/507)'s first open question. Request bodies are strict and responses only gain fields, so a breaking change means `/api/v2`. The contract also marks the request fields that carry a secret, so the fingerprint a receipt keeps of a request never hashes one.
- **The wire shapes.** The v1 error envelope and its closed codes (`{error: {code, message, retryable, …}}`, with `needs` naming a missing permission, `current` the present state on a conflict, and `verb` the real CLI twin); the list envelope (`items`, `next`, `snapshotAt`, and `truncated` and `empty` notes, so a cut-short or empty list says why, `empty.reason` being one of `no-data`, `no-access`, `unsupported`, `filtered`, `not-indexed`, `unreachable` or `expired`); `EXIT_FOR_ERROR`, total over the error codes, which gives each a CLI exit (the band 50-56 in `errors`: 50 not signed in, 51 forbidden, 52 unavailable, 53 conflict, 54 unsupported, 55 refused, 56 not found; 38 and 39 keep their meaning, and internal errors stay 1); the command receipt and the closed registry of command kinds, each with its permission, whether it is idempotent, whether its effect is local or external, and its twin; and the capability descriptor (`{supported: true, mode?}`, `{supported: false, reason, verb}`, or `{supported: "unknown", reason}` for a bundle built before the support manifest) with its closed set of names, so a control a bundle cannot enforce shows as "recorded, not enforced" rather than as done. `SHAPE_RUN_CONTROLS` is the one per-shape table of run controls.
- **Events and cursors.** The envelope every control-plane event carries (`{v, id, eid, type, at, …, sensitivity}`: refs, plus a small masked payload or a reference to one) and the versioned taxonomy, closed per build. Families come through modules, each type with a sensitivity; the core's module brings `run.*`, `decision.*`, `command.*`, `deployment.*`, `harness.*`, `access.changed`, `stream.{gap,reset,pause}` and `auth.{expired,revoked}`, and feature areas bring theirs as they land. Trace events are wrapped as `run.trace` when read, so no producer changes, and people events never carry values. `eid` gives an event one identity: `evt_` plus 26 Crockford characters of a SHA-256 over its scope, source, segment, byte offset and a short digest of its line, computed on read, so it is the same in run, harness and fleet streams and after an index rebuild, and clients drop duplicates by it. It never authorizes anything. Each event type is `internal`, `restricted` or `people`, which `sensitivityOf` answers; trace frames take theirs from `TRACE_KIND_SENSITIVITY`, where an unlisted kind is `restricted` and a test fails until it is listed. Frames with text need `h.read.content`, and content-free frames are metadata. `people` fails closed: such an item is released only when the registered people domain allows `people.derived.read` on its ref, and with none registered it is withheld and the answer says `hidden: ["people"]`. The **cursor codec** encodes a stream's position as the opaque string an SSE `id:` and `Last-Event-ID` carry, and decodes it again. For a run or harness stream the position is an offset into each file the stream reads, each with a short hash of the bytes before it, so a resumed stream can tell that a file changed under it; for the fleet stream it is an epoch and a sequence number.
- **Field names that survive the masker.** Hangar masks every response by key name, so a contract field named like a credential would come back masked. Fields are named around it (`environment`, `dedupeRef`, `fingerprint`, `resumeScope`, `askDigest`, `credentialRef`, `prefixHint`; `signIn`, not `auth`, in the discovery document; `deviceJwk`, not `publicKey`, for a device's public key); a test walks every field of every schema through `isCredentialKey` and fails on a hit, unless the contract marks the field as carrying a secret; the matcher is never widened or narrowed.

Does not own: reading or writing anything — record formats, locks, claims, segments, tail readers, the file positions a cursor encodes, and reporting a gap or a reset (`control-records`, brief 324; no other package opens a control file directly); principals, credentials, grants, links, `authenticate()` and `authorize()` (`access-control`, brief 323); running anything — the command executor and recovery, the decision service (supersede, deadlines, fallbacks, standing rules), deployments and activation, operator controls, retire, the ref resolver, the projector and its streams, and computing a harness's capabilities from `SHAPE_RUN_CONTROLS`, all composed by `wireControl` (`control-service`, brief 325); first-decision-wins for tool approvals, the consume claim and the decision log (`session-store`, with runtime-core parking and consuming directly and calling `verifyDecision` first); the HTTP layer — the choke point, the route table for the legacy `/api` routes, which keep their own shapes, the handlers and masking at the exit (`hangar-server`); the daemons' `crewhaus.control.v1`, server and client (`gateway-protocol`), and the managed `crewhaus.v1` (its wire contract in `gateway-protocol`, its server in `gateway-server`); classifying run input that arrives through the API, at TrustOrigin `api` — the contract only names the `input_blocked` code a refused input answers with; and the SDK package itself.

## Inputs and Outputs

Inputs: strings to check, parse or classify (ids, refs, cursors); records the caller has already read (run rows; a decision with its overlays, its binding and the approver projection) together with the consuming run's scope, revisions and places, and the current time; and a request or response body for `./schemas`.

Outputs: minted ids; parsed refs and run-id families; transition verdicts; effective run and decision states; a `verifyDecision` verdict, a pass or the failed check's reason; the area modules, the operation table, the command kinds, the permission vocabulary, the role matrix, the event taxonomy, the exit map and the capability names as plain data; rendered and parsed twins; event ids and sensitivities; error, list and event envelopes; encoded and decoded cursors; and the zod validators.

## Dependency Notes

None from `.` or `./http`, by design: the dependency-free discipline of `claim-ledger` and `qr-code`, plus one more constraint, Node-clean source (relative `.js` specifiers, no `Bun.*`, no `node:` import, held by a NodeNext type-check), which is why randomness comes from `crypto.getRandomValues`. `./schemas` depends on `zod`, already a workspace dependency: the package lists it in its `dependencies` for that entry point alone, and nothing in `.` imports it, so bundling `.` never pulls it in. No existing package could take the role: `gateway-protocol` depends on zod and event-log and its `./control` entry imports `node:fs`, and `hangar-server` is the console's server, which a harness must never depend on.

Consumers: `control-records` (324), `access-control` (323) and `control-service` (325) build on it; `run-context` and `runtime-core` take `mintRunId` from it, and runtime-core `verifyDecision`, inside compiled bundles; `session-store` and `hangar-server` re-export their `sess_` and `appr_` grammars from it; `hangar-server` checks `crewhaus.hangar.v1` requests with `./schemas` and publishes the table; `apps/cli` drives operations through `crewhaus api`, over `./http`; and `@crewhaus/client` bundles `.`. Home's UI never imports it: it reads the table from the discovery document.

Every package that imports it declares it in its own `dependencies`, checked on the installed tarballs as well as the checkout, because an undeclared workspace import works in the tree and breaks only once published. A compiled bundle's `package.json` pins only the `@crewhaus/*` packages the bundle imports directly (`apps/cli/src/bundle-manifest.ts`), so session-store, run-context and runtime-core taking this dependency moves no bundle byte. Top-level run ids do change shape once run-context's default minter becomes `mintRunId()`; the PR that makes that switch lists it as a default-on change, and consumers such as [crewhaus/ui](https://github.com/crewhaus/ui) must treat run ids as opaque.

## First Implementation Slice

One of the first PRs of the control core's train ([#507](https://github.com/crewhaus/factory/issues/507)); it needs no earlier PR. It lands the package, scaffolded like its siblings from `packages/routing-store/package.json`, as data, types and tests only, and wires its first callers in the same change: `session-store` and `hangar-server` re-export the `sess_` and `appr_` grammars from it instead of declaring their own. `src/areas/index.ts` starts with one commented placeholder per known area, each on its own line between blank lines, so an area's first change edits only its own line. It changes no behaviour, makes no default-on change and moves no pinned fixture byte.

The other callers arrive with the PRs that need them: `control-records` (brief 324) first; then `access-control` (brief 323), run-context's default minter, runtime-core's consume check, `control-service` (brief 325) and hangar-server's route table; and last the `crewhaus.hangar.v1` handlers, with discovery and `crewhaus api`. `EXIT_FOR_ERROR` arrives with receipts, `./http` and `SHAPE_RUN_CONTROLS` with the v1 API, and `eid` and `sensitivityOf` after the streams. This brief lands in crewhaus/docs before the package does, as the factory's rule for new packages requires.

## Validation Plan

Catalog tests: T1, T2, T9. The walks below iterate `AREA_MODULES` and assert their counts, so they cover the next area by construction. Primary risks: **two surfaces disagreeing about an id or a state** — answered by one owner, round-trip tests that mint, print, parse and classify freshly minted ids, the pin test over the known copies, and `scripts/run-id-families.test.ts`, which feeds `classifyRunId` ids from the real minters, citation-tracker's `newRunId` (`packages/citation-tracker/src/index.ts`) among them, rather than hand-written ones, because a hand-written fixture cannot catch a minter's real shape; **a state an object can enter and never leave** — a test that every non-terminal state reaches a terminal one; **a field the masker hides** — the walk of every field name through `isCredentialKey`; **an operation the table and the server describe differently** — the table's self-consistency test here (every permission is in the vocabulary, every twin is real or `null`), the twin round-trip through `renderTwin` and `parseTwin`, and, once the handlers exist, the server's test that every operation has a handler, a permission and a twin or `null`, and every handler an operation; **an error a script cannot read** — a test that fails on an error code with no exit; **free text that reaches a model undeclared** — the `modelBound` canary, which lands with the first operation declaring one and sends a canary through every free-text field of the composed table; and **a consume check that passes what it should refuse** — a test per `verifyDecision` reason, each able to fail on its own.

Definition of done: `bun test packages/control-contract/src` green; `.` importing no package and no `node:` module, with zod reachable only through `./schemas`; the round-trip, reachability, run-id-family, grammar-copy pin, field-name, operation-table and twin tests green over `AREA_MODULES`; and session-store and hangar-server re-exporting the grammars with their own suites unchanged.
